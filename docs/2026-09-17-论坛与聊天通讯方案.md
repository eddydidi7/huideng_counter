# 慧灯计数器：论坛与聊天通讯实施基线

日期：2026-09-17。状态：需求与设计已确定；本文不是功能完成报告。

## 1. 命名和菜单
统一中文名「聊天通讯」，英文「Chat」。应用、后台、提示、设置及新数据库注释保持一致。技术表名 conversations/messages 可保持稳定，不为改中文名破坏结构。
「我的」最终顺序：
1. 供佛 / 供灯
2. 共修
3. 论坛
4. 聊天通讯
5. 网盘
6. 账号与同步
7. 云同步与存储
8. 收藏
9. 关于与联系
10. 设置
供佛和共修不得删除。供佛沿用后台可修改的现有 HTTPS 配置。收藏保留个人笔记收藏，后续另分论坛收藏。新模块完成后接入，不用无法使用的按钮冒充功能完成。

## 2. 当前实际实现
- 用户端 Flutter 当前论坛入口启动外部网站，尚无原生帖子、回复、点赞、用户主页。
- 管理端论坛页也尚未接入外部网站管理 API。
- 聊天通讯和个人网盘尚无实现，没有可直接改名的运行时代码或数据表。
- 全局明暗色、账号、计数、笔记及公开笔记功能保留；不迁移或覆盖私人数据。
- 原生社区建在当前 Supabase 项目中；旧外部论坛内容不会被自动抓取、导入或删除。网页账号不能凭相同邮箱自动视为 Supabase 身份。

## 3. 论坛第一版
视觉：沿用慧灯柔和色彩、明暗主题、Material 图标和现有排版，不复制其他平台品牌或页面。
首屏：搜索框、推荐/最新切换、横向分类、单列内容卡片、发布按钮。关注未实现前不显示空的可点击标签。
分类：学修交流、佛法问答、共修活动、修行心得、资料分享、建议反馈。
卡片：有图显示首图封面，无图显示文字；标题、摘要、作者头像/昵称、发布时间、点赞/回复数、收藏状态。
详情：作者、时间、标题、正文、横向图片翻页、标签、回复；底部固定回复/点赞/收藏/分享。
发布：标题、正文、1—9 张图片、标签、分类；九宫格预览、上传失败保留草稿、不重复发布。
搜索：标题、正文、标签、作者昵称；中文子串可用；服务端分页查询，不只过滤已加载的几条。
推荐：第一版确定性排序，置顶/管理员推荐优先，再结合发布时间及互动数；保留稳定 UUID 排序兜底，不引入 AI 或个性化。
注册用户：统一 Supabase Auth，固定昵称头像、我的帖子/回复、点赞、收藏、回复提醒、编辑/软删除自己的帖子。
游客：公开浏览搜索；发帖/回复不要求填写邮箱密码；可选昵称，默认游客。游客身份必须由服务端验证，不相信客户端传来的任意 visitor_id。
管理员：置顶、推荐、隐藏、软删除、锁定、关闭回复、禁言、拉黑、举报处理；高权限经安全 API，操作留审计。
第二版：双列瀑布流、关注/取消关注、关注流、排序完善。个性化推荐另行评估。

## 4. 数据结构草案（实施时新增 migration）
| 表 | 主要字段及约束 |
|---|---|
| profiles | user_id 对应 auth.users、nickname、avatar_path、created_at、updated_at；角色/状态仅管理员修改 |
| forum_categories | id、slug 唯一、中文/英文名称、排序、enabled |
| forum_posts | UUID、author_user_id 或受验证游客标识、category_id、title、body、created_at、updated_at、deleted_at、version、visibility、is_pinned、is_recommended、is_locked、comments_closed |
| forum_post_images | UUID、post_id、storage_path、position、width、height；最多九张；不接受任意他人路径 |
| forum_tags / forum_post_tags | 标签及帖子关联，关联唯一 |
| forum_replies | UUID、post_id、author_user_id/游客、body、created_at、updated_at、deleted_at、visibility、version |
| forum_likes | user_id + post_id 唯一，避免重复点赞 |
| forum_bookmarks | user_id + post_id 唯一，仅本人读取收藏集合 |
| forum_notifications | UUID、recipient_id、post_id/reply_id、read_at；仅接收人读写已读状态 |
| forum_restrictions | 注册用户或受验证游客、禁言/拉黑、原因、到期时间、管理员；仅后台写 |
| forum_reports | UUID、目标、提交人、原因、状态；举报人只能查看自己的提交，管理员处理 |
| user_follows | follower_id + followed_id 唯一，禁止关注自己；第二版使用 |
| forum_request_receipts / rate_limits | 请求幂等、主体和时间窗口；服务端维护，无客户端直接写权限 |

公共读取只返回已发布、未隐藏、未删除内容；不公开邮箱、Auth 信息或管理员内部字段。私有草稿、收藏、提醒和个人文件采用账号隔离。
写入服务在一次事务中检查账号/游客身份、限制状态、目标帖状态、限频、版本与请求 UUID，防止客户端绕过按钮直接调用。点赞/回复数由真实关联记录计算或原子维护，不接受客户端上报最终数。
编辑使用版本检查，冲突不静默覆盖；删除采用 deleted_at。管理员字段与作者字段分开权限。
图片先上传受控对象，再确认发帖；失败时保留本地草稿。清理未引用图片另设保留期，不能把用户已发布资源自动永久删除。
本地草稿/发送队列需 SQLite migration；公开浏览缓存复用 public_content.sqlite，私人草稿不能放公共缓存。

## 5. 游客防刷与统一账号
优先评估同一 Supabase Auth 的匿名身份，不要求游客注册。需单独评估其对当前账号切换和 RLS 的影响；不能为了游客论坛把已有计数/笔记账号静默切走。
如使用匿名 Auth，应区分 is_anonymous 与永久账号；visitor_id 是服务端身份关联，不是客户端生成 UUID 即可获得权限。
发布/回复另做服务端限频；注册用户和游客均受限制。达到阈值要求验证码，客户端不保存验证码 secret。
官方依据：
- https://supabase.com/docs/guides/auth/auth-anonymous
- https://supabase.com/docs/guides/auth/auth-captcha
本次没有启用匿名注册、改变 RLS 或发布写入接口。

## 6. 聊天通讯与文件
统一 Supabase Auth，不建设第二套注册登录。
阶段功能：好友申请/列表、单聊/群聊、文字/图片/文件、时间、已读未读、撤回、置顶、免打扰、黑名单、举报、红点。Realtime 用于变化通知，消息以数据库记录为准；重连须从持久化游标补拉。
草案表：friend_requests、friends、conversations、conversation_members、messages、message_reads、user_blocks、chat_preferences、chat_reports；成员权限决定谁能查看会话和附件。撤回保留撤回状态，不能承诺删除接收方已下载文件。
大文件双方在线时优先 WebRTC DataChannel，按块传输、哈希校验、取消/进度/失败恢复；信令按会话成员授权。上线前验证连接中继及移动网络适配，不承诺所有网络均能直连。
小文件和离线文件通过存储适配层：Supabase Storage、OSS、COS、Cloudflare R2；私有对象和短期授权下载。Google Drive 保留为个人备份。
R2 是新增的聊天附件后端选项，不在本次擅自移除或替换原四项个人存储服务。
暂不做语音/视频通话、朋友圈、红包或位置共享。

## 7. 代码分层与交付顺序
保持现有工程。forum/domain 模型，forum/data/local 草稿/缓存，forum/data/remote 云接口，forum/data/repository 聚合，forum/presentation 页面。Chat 使用同样分层，复用当前 Auth。
先交付论坛纵向流程：分页卡片 → 详情 → 注册用户发布图片与回复 → 点赞/收藏 → 搜索/主页 → 游客身份及防刷 → 管理端治理 → 真机与 Windows 验收。未达到完整第一版前不宣布论坛完成。
每阶段报告修改/新增文件、package、SQLite migration、Supabase SQL/RLS、后台设置、凭据需求、真机结果、剩余项及迁移风险。
